# Architecture

## Layers and dependencies

- `SmartInbox.Domain`: the `InboundMessage` aggregate, status, transitions, attachment metadata, and domain limits. It depends only on .NET.
- `SmartInbox.Application`: commands, queries, FluentValidation validators, validation behavior, `TimeProvider`, and the `IInboundMessageRepository` contract.
- `SmartInbox.Infrastructure`: EF Core configurations, `AppDbContext`, PostgreSQL migrations, repository, and validated `[IoC]` scanning.
- `SmartInbox.API`: composition, v1 contracts, bearer token authentication, HTTP limits, `ProblemDetails`, and Minimal API endpoints.

Application does not depend on Infrastructure. The API is the composition root and references Application and Infrastructure. The domain has no dependency on HTTP or EF Core.

## Aggregate and fingerprint

`InboundMessage.Receive` creates the initial `Received` status, obtains `ImportedAt` from `TimeProvider`, and converts both timestamps to UTC. `Source` is trimmed and lowercased; `MailboxId`, `ExternalMessageId`, and `ExternalThreadId` preserve their casing because they are opaque external IDs. The body and subject are preserved without rewriting. Empty optional fields become `null`; MIME types are trimmed and lowercased.

The SHA-256 fingerprint is calculated from a deterministic JSON representation of `Source`, IDs, sender, subject, body, UTC `ReceivedAt`, and attachment metadata. It excludes the internal ID, status, and import time. Thus, a repeated message retains the same fingerprint when it arrives in a later run.

The status flow allows `Received -> Processing -> Processed/Failed` and `Failed -> Processing`. Processing state, retries, lease data, and the single current classification belong to `InboundMessage`; no separate processing aggregate is needed. Classification is a bounded value object containing explicit facts, missing information, warnings, uncertainty, and typed review reasons. `RequiresReview` is derived from those reasons.

## Idempotency and transactions

PostgreSQL enforces the unique index `ux_inbound_messages_source_mailbox_external_message_id` on `(Source, MailboxId, ExternalMessageId)`. The application does not depend on a prior lookup.

1. The repository attempts to insert the message.
2. If PostgreSQL commits the write, the API returns `202 Accepted`.
3. If PostgreSQL returns `23505` for the idempotency index, the repository detaches the failed entity and queries the persisted record.
4. If the record exists and the fingerprint matches, the API returns its ID with `200 OK`.
5. If the record exists but the fingerprint differs, the application returns `409 Conflict`. The row is not updated.
6. If the collision is unrelated to the expected index or the record cannot be found after the collision, the error propagates to the exception handler.

The concurrency test uses two independent scopes and `AppDbContext` instances against PostgreSQL. Another test inserts two rows directly to verify that PostgreSQL's unique index rejects the second row.

## Persistence

The initial migration creates `inbound_messages`, status and fingerprint constraints, and idempotency and date indexes. Timestamps use `timestamp with time zone`; the repository writes only UTC `DateTimeOffset` values. Normalized attachment metadata is stored as `jsonb`; there is no column for file bytes.

Migrations are applied explicitly with `dotnet ef database update`. No environment runs implicit migrations when the API starts.

## Phase 3 review design

The implementation follows these review boundaries:

- A `WorkItem` is a separate aggregate linked one-to-one to an inbound message. Successful classification creates it in the same database save that marks the message `Processed`; failed and in-flight messages cannot enter the queue. A unique source-message constraint makes concurrent completion safe. The original `EmailClassification` remains unchanged, and its `RequiresReview` value continues to describe only the original AI result.
- A work item stores effective category and priority, typed reviewer-managed facts with explicit verification state, bounded notes, lifecycle, and an integer concurrency version. Review changes and their append-only audit entry commit together.
- A work item has one internal response draft with immutable numbered revisions. Each edit appends an unapproved revision; approval or rejection applies to that revision and records the reviewer. An approved revision remains visible after later edits. The recipient is copied from the inbound sender and is not generated by AI. Approval never sends or creates an external draft.
- The API uses ASP.NET Core cookie authentication for one configured local reviewer. The stable reviewer ID comes from server configuration, and the login secret stays in User Secrets or the process environment. Review policies accept only the reviewer cookie scheme; the existing service-token scheme remains for message ingestion and cannot approve drafts. Sessions expire after one hour, cookies are `HttpOnly` and `SameSite=Strict`, and every state-changing browser request requires an ASP.NET Core antiforgery token.
- The Next.js app calls the API through a same-origin rewrite, so browser code receives neither the service token nor the OpenAI key. This keeps local setup small and avoids cross-origin cookie configuration.
- Optional AI drafting is disabled by default. An explicit reviewer request uses the existing Responses client through a provider-neutral application port, one request at a time, with a bounded output size and no automatic provider retry. It creates an unapproved draft revision, uses only verified reviewer facts for definitive business statements, and records provider telemetry without source text.

This is a single-operator localhost design, not production identity management. Its trade-off is that local credentials and one configured reviewer are sufficient for the synthetic demo, while multi-user provisioning, rate limiting, TLS deployment, key rotation, and enterprise session management remain future work. Human corrections and audit history are stored separately from the source message and its immutable classification; retention or deletion must therefore account for both records.

### Phase 3 implementation

- Domain types are in `SmartInbox.Domain/WorkItems`. Application commands, validators, projections, and ports are in `SmartInbox.Application/WorkItems`; EF records, configuration, mapping, and the repository are in `SmartInbox.Infrastructure/WorkItems/Persistence`.
- `CompleteProcessingAsync` inserts the `WorkItem` and its initial audit entry in the same transaction as classification and the `Processed` status. A unique index on `SourceMessageId` prevents duplicate queue entries. `20261021122611_AddHumanReviewAndDrafts` backfills already processed messages, facts as unverified, and a system creation event.
- Work item updates use an integer concurrency token. The application requires the client's `ExpectedVersion`, and PostgreSQL's concurrency check rejects a stale update. A successful aggregate update, appended draft revisions, and appended audit events share one save. Review history is returned in time order; application operations do not update or delete audit rows.
- Drafts contain immutable numbered revisions. Each save creates an unapproved revision, decisions can only target the current revision, and old approved revisions remain distinguishable. Recipient context comes from the inbound sender; the AI adapter never receives or chooses an address. No API route sends or externally creates an email.
- Reviewer endpoints live under `/api/v1/reviewer`; work item endpoints live under `/api/v1/work-items`. The latter use only the `ReviewerCookie` scheme and `HumanReviewer` policy. The service-token scheme remains the default for `/api/v1/messages`. Cookie-backed login, logout, and all review mutations validate the `X-CSRF-TOKEN` antiforgery header. The server exposes whether AI drafting is enabled in the authenticated session response so the UI can hide the action when disabled.
- The Next.js App Router UI is under `web/src/app` and calls same-origin `/api/*` paths; `web/next.config.ts` forwards them to the local API. The browser never receives a service token or OpenAI key. The panel renders source bodies as plain text and displays only a generic processing diagnostic alongside the safe failure kind.
- `EmailDrafting:Enabled` defaults to false. The reviewer must request generation explicitly. The OpenAI Responses adapter is bounded by input and output limits, concurrency and timeout options, performs no automatic retries, and stores only bounded provider/token/cost metrics with the unapproved revision. An interrupted provider request can still have been billed; clients should not automatically resubmit it.

The audit log summarizes decisions and references facts, drafts, and revisions without copying email bodies, credentials, prompts, or provider responses. There is no retention scheduler or review-history deletion workflow. Deleting a source message cascades through its work item and history, so future retention work must define coordinated deletion, legal hold, and export behavior before using real data.

## Phase 4 Gmail and Outlook integration

- n8n polls Gmail with the Gmail Trigger in full-message mode, maps its provider message ID and thread ID separately from the RFC `Message-ID`, and calls `POST /api/v1/integrations/gmail/messages`. The API supplies the one configured source and mailbox; the request cannot select another mailbox. PostgreSQL's existing `(Source, MailboxId, ExternalMessageId)` index remains the only idempotency authority. The workflow excludes sent, draft, spam, trash, and non-inbox mail, does not change read state or labels, and does not download attachment bytes.
- Gmail OAuth lives in n8n. Gmail and Outlook integration tokens, the generic service token, and reviewer password must be unique across enabled schemes; startup validation enforces this. Reviewer-created export intents and manual reconciliation use the existing reviewer cookie and antiforgery protection. Service tokens cannot approve drafts; no integration token or provider credential reaches browser code.
- `GmailDraftExport` pins subject, body, exact recipient, destination mailbox, and current approved revision into a fingerprinted PostgreSQL row. A unique index scopes idempotency to draft, revision, mailbox, and recipient. The claim uses a row lock and lease. Editing the draft cancels unstarted requests transactionally. The worker consumes only the persisted snapshot; n8n does not choose content or recipients.
- An external Gmail create call is not idempotent. A timeout, missing result ID, or expired in-progress lease transitions to `NeedsReconciliation`; it is never automatically re-claimed. A reviewer records a found draft ID or confirms the mailbox was checked and no draft exists before authorizing a retry. This provides at-most-one automatic create attempt per claim, not exactly-once creation across Gmail and PostgreSQL.
- `POST /api/v1/work-items/{id}/draft-exports` is a separate reviewer action after current revision approval. Approval itself has no external side effect. The n8n workflow uses only Gmail `Draft/Create`; there is no Send, Reply, Forward, Delete, or Trash operation. The MVP creates a standalone draft because the message contract does not preserve the headers needed to establish Gmail reply threading safely.
- `GmailIntegration:Enabled` defaults to false. `SMARTINBOX_GMAIL_MODE` defaults to `disabled`; `fake` uses a synthetic draft ID and `live` selects the Gmail node. Both imported workflows remain inactive. The Compose `integrations` profile binds the editor to loopback and stores n8n credentials and its generated encryption key in a separate named volume. See `integrations/n8n/README.md` for OAuth and activation controls.

- Outlook uses the same inbound-message and internal draft workflow behind provider-specific `/api/v1/integrations/outlook/*` routes and separate service tokens. The API supplies the configured source and mailbox; `(Source, MailboxId, ExternalMessageId)` keeps Graph IDs distinct from Gmail IDs. Outlook's RFC `internetMessageId` and recipient list are stored as supplemental metadata, while `conversationId` remains a thread identifier and never the idempotency key.
- Outlook polling uses delegated Microsoft Graph access in n8n, verifies `/me` against the configured mailbox, and lists only a configured custom test folder after a local UTC cutoff. `Prefer: IdType="ImmutableId"` and text-body preference are sent on folder reads; Graph pagination follows `@odata.nextLink`. The fixed cutoff deliberately re-reads the small folder on each poll, so this MVP has no durable delta checkpoint and is not intended for a broad or growing mailbox.
- Outlook export is provider-scoped in persistence and callbacks. The reviewer explicitly selects Outlook and confirms the configured mailbox, recipient, and approved revision. n8n posts the persisted subject/body/recipient to Graph `POST /me/messages`, accepts only a `201` response with an ID and `isDraft=true`, and never sends. An uncertain result enters `NeedsReconciliation`; Graph draft creation is not exactly-once and there is no automatic search across the mailbox.
- `OutlookIntegration:Enabled` and `SMARTINBOX_OUTLOOK_MODE` default to false/`disabled`; both Outlook workflows are inactive on import. Live reads require a non-system test-folder ID, a UTC cutoff, the configured mailbox, and an identity match. See [OUTLOOK_TEST_SETUP.md](OUTLOOK_TEST_SETUP.md) for personal Microsoft account setup and controlled activation.

Google's Gmail `gmail.compose` scope includes sending capability, and Microsoft's delegated `Mail.ReadWrite` permits broader mailbox writes, even though these workflows only create drafts. Use separate minimal delegated credentials and verify their account identities before live testing. Outlook performs a runtime `/me` mailbox check; Gmail account matching remains an operator setup check.

## Classification and provider boundary

The API persists an inbound message before background processing can claim it. `InboundMessageBackgroundService` starts no worker loops unless `EmailProcessing:Enabled` is true. Its bounded workers create a fresh dependency injection scope for each poll, so each claim and result write uses a short-lived `AppDbContext`.

`IEmailAnalyzer` selects the provider through `IEmailAnalysisProviderFactory` and applies `EmailAnalysisPolicy` to the returned candidate. Domain and Application contain no OpenAI SDK types. The OpenAI adapter uses the official .NET SDK Responses API with strict Structured Outputs JSON Schema. Email subject and body are explicitly treated as untrusted input. Provider output is integration data; it is parsed, size-checked, enum-checked, and validated against source text before becoming a domain classification.

The policy rejects malformed candidates, maps unsupported category values to `Unknown`, and requires review for unknown, ambiguous, incomplete, contradictory, unsupported, or warned results. Extracted fact values must occur in the source message. Elevated priorities require an exact source quote containing supported urgency language; unsupported elevations are downgraded and marked for review. `Processed` means processing completed, not that a person approved the classification.

## Background work, leases, and retries

`ClaimNextForProcessingAsync` selects one eligible row with PostgreSQL `FOR UPDATE SKIP LOCKED`, updates its attempt count and lease owner/expiry, and commits before any provider call. A second worker skips the locked row. A crashed worker's message becomes eligible after lease expiry, subject to the configured attempt limit. When the final lease expires, the row is marked failed with `RetryLimitReached`.

Completion and failure writes lock the row and require the current lease owner. A stale worker therefore cannot replace a result after another worker has reclaimed the message. Classification and message status are written in one transaction, with a one-to-one primary key on `email_classifications.MessageId`. The provider call never runs inside a database transaction. Idempotent ingestion returns the existing message and does not enqueue a second successful classification.

Connectivity, rate-limit, and timeout errors can retry after a fixed configured delay, up to the attempt limit. Authentication, unsupported provider/model, invalid structured output, and other non-transient errors stop immediately. Cancellation requested by the host propagates. The provider client retry policy is disabled so the persisted worker retry count remains the spending bound. Available provider/model, duration, token usage, and configured-price estimate are stored on the message; the database keeps the latest available provider metrics and total attempt count, not a full event history. Cost stays unknown unless matching pricing is configured.

The worker provides at-least-once execution around the external provider call. A process crash after the provider completes but before the classification transaction commits can repeat that in-flight request after lease expiry. Once a result is committed as `Processed`, normal retries and duplicate ingestion cannot claim it again.

The worker defaults to disabled. When enabled, startup validates the provider identity, required OpenAI key, model ID, output limit, processing limits, and pricing configuration. The OpenAI key is not included in repository configuration. Message endpoints remain protected by service authentication; no unauthenticated route can trigger provider spending.

## API and security

- `POST /api/v1/messages`, `GET /api/v1/messages/{id}`, and `GET /api/v1/messages` require a bearer token configured outside the repository.
- The token must be at least 32 characters long; comparison uses SHA-256 hashes and a fixed-time comparison.
- `GET /health` does not require a token and checks PostgreSQL connectivity.
- HTTP request bodies are limited to 65,536 bytes. Character-limited fields and pagination are validated in Application.
- Unknown JSON properties are rejected so unsupported binary fields cannot be silently accepted.
- Validation errors, conflicts, missing records, and unexpected failures produce stable responses. Internal exceptions and exception messages are not returned to clients.
- Application logs record the type of an unexpected exception, not its payload or message. EF Core sensitive-data logging is not enabled.
- Provider logs record outcome and bounded telemetry but omit email content, sender addresses, prompts, output bodies, API keys, and raw provider exception messages.

The token does not provide user identity, mailbox-level authorization, rotation, auditing, or abuse controls. Email bodies are stored as plain text. This remains a private local demo using synthetic content.
